\section{Problem Statement \& Swarm Vulnerability}
% ------------------------------------------------------------------
\label{sec:problem}

Ground- and air-launched autonomous swarms executing self-protecting perimeter defense are asked to make aggressive, coordinated maneuvers under contested electromagnetic conditions. Aggressive AI-driven controllers---whether model-predictive, reinforcement-learning, or hybrid---naturally command actuator demands that approach or exceed physical limits. In a swarm, the consequences are not limited to a single airframe:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Dynamic actuator saturation:} A commanded roll/pitch/yaw/thrust mix can demand motor PWM values beyond the ESC envelope. When saturated open-loop, one rotor starves while another over-commands, producing unmodeled torque and rapid attitude divergence.
    \item \textbf{Mid-air vehicle desync:} Without a deterministic, independent safety boundary, two drones responding to the same perceived threat may simultaneously command limit excursions in coupled directions, breaking the geometric spacing the swarm controller assumed.
    \item \textbf{Catastrophic cascade collisions:} A single saturated drone that loses altitude or yaw stability can cross into a neighbor's keep-out sphere; the neighbor's evasive maneuver may then saturate \textit{its} actuators, turning a localized limit breach into a multi-vehicle cascade.
\end{enumerate}

Existing swarm architectures rely heavily on centralized planners or inter-agent RF coordination to prevent these outcomes. Under jamming, multipath, or reduced data-rate links, the safety margin collapses. ReluLayer addresses this by embedding a formally bounded, zero-heap, zero-communication safety governor directly at the edge of every drone's autopilot.

\subsection{Air-Drop Deployment \& Swarm Scale Compliance (Oct 4 DSIP Q\&A)}
\label{subsec:qa}

The ReluLayer-governed swarm is designed explicitly for the air-launched operational envelope defined in the \textbf{October 4, 2026 DSIP Q\&A}:

\begin{itemize}[leftmargin=*]
    \item \textbf{Vehicle Gross Weight:} Each drone remains bounded at \textbf{$< 50\ \text{lb}$ ($< 22.7\ \text{kg}$)}, inclusive of airframe, Pixhawk 6X flight computer, battery, and deployment latching hardware.
    \item \textbf{Air-Drop Deployment Kinetics:} Selected test envelope points are bounded strictly within \textbf{3,000--10,000 ft MSL} and \textbf{130--200 KIAS} airspeed.
    \item \textbf{Host Aircraft Relationship:} The host platform (C-130J via un-modified paratroop doors/ramp) departs immediately post-release. ReluLayer independently arrests post-drop freefall trajectories and establishes swarm operations with \textbf{zero co-flight period} and \textbf{zero reliance on host RF}.
    \item \textbf{Minimum Swarm Scale:} The architecture is designed for \textbf{$\ge 10$ simultaneous heterogeneous agents}, with SITL demonstrations already supporting \textbf{50+ agents} with distributed sensor allocation across airframes.
\end{itemize}

\subsection{Architecture}

The Python package \texttt{relulayer} exposes a \texttt{Governor} class whose \texttt{project()} method calls the \texttt{\#![no\_std]} active-set projection core through a C-compatible dynamic library. \section{Sprint 4 --- Multivariable 4-D Coupled QP Solver \& Zero-Heap Discipline}
% ------------------------------------------------------------------
\label{sec:sprint4}

Sprint 4 extended the scalar active-set boundary to a coupled four-channel polytope solver required for thrust-limited, geometrically constrained swarm allocation.

\subsection{Problem Formulation}

The 4-D QP projects a raw actuator demand $u_{\text{raw}} \in \mathbb{R}^4$ onto the feasible set defined by per-channel bounds and a coupled linear inequality such as a total-thrust ceiling:
\begin{equation*}
\min_u \frac{1}{2} \|u - u_{\text{raw}}\|_2^2
\quad \text{s.t.} \quad
u_{\min} \le u \le u_{\max},
\quad \sum_{i=1}^4 u_i \le T_{\max}.
\end{equation*}

\subsection{Empirical Benchmark}

A host-side Monte Carlo harness generated 1,000 randomized 4-D demand vectors and solved each instance through the C-ABI entry point.

\subsection{Zero-Heap Discipline}

The kernel enforces allocation-free execution at three levels:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Crate-level \texttt{\#![no\_std]} / \texttt{\#![no\_main]}:} The production embedded build disables the Rust standard library and OS runtime. Entry points are \texttt{[no\_mangle]} C-ABI functions invoked from PX4 or bare-metal startup code.
    \item \textbf{Static stack-frame bounds:} All working memory is declared as fixed-size arrays on the stack ($u_{\text{safe}}[4]$, working-set arrays of length $W_{\max} = 8$, normal-equation matrices $8 \times 8$). No \texttt{Vec}, \texttt{Box}, \texttt{Rc}, \texttt{Arc}, or allocator API appears in the hot path or solver modules.
    \item \textbf{Compiled-object verification:} The release embedded profile sets \texttt{panic = "abort"}, \texttt{lto = true}, and \texttt{opt-level = 3}. A post-link disassembly inspection of the \texttt{.text} section confirms only Thumb-2 instructions; \texttt{.data} and \texttt{.bss} contain zero dynamic allocations attributable to the solver. Panic paths abort via an infinite loop rather than invoking an unwinder or allocator.
\end{enumerate}
